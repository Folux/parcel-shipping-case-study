# Parcel Shipping Platform Case Study

## Overview

You are building a feature set for a parcel shipping platform that needs to be delivered in **6-8 hours maximum**. The focus is on **MVP-style delivery** with functional coverage rather than polish. All required points must be addressed, but in minimal viable form.

**📋 Full case study requirements**: See `instructions/case-study.md`

**📁 Project Structure**:
- Specifications: `planning/specs/SPEC_*.md`
- Implementation Plans: `planning/implementation/IMPL_*.md`
- Progress Notes: `notes/Pirate_Ship_case_study_notes.md`

### Key Context
- **Platform**: Parcel shipping platform  
- **Primary Market**: United States (domestic shipping at cheaper rates)  
- **Secondary Market**: Global shipping (edge case, lower priority)  
- **Interview Goal**: Demonstrate thoughtful design, pragmatic prioritization, and shipping-ready code

## Critical Working Methodology

⚠️ **FOLLOW THIS PROCESS STRICTLY:**

### Phase 1: Specification (Spec Document)
- Define each component and what it must do
- No implementation details yet
- Clear acceptance criteria
- Identify dependencies between components
- **Output**: Complete spec document ready for review

### Phase 2: Implementation Plan
- Design how each component will be built
- Technology choices (if relevant)
- Integration points
- Sequencing for efficiency
- Risk assessment
- **Output**: Clear step-by-step implementation plan

### Phase 3: Implementation
- Build one component at a time
- Test as you go
- Keep it MVP—if it does the job, move on
- Document as you build

### ⭐ THE GOLDEN RULE
**Work on ONE step at a time.** 
- You (the user) review and approve each step before we move to the next
- Do NOT write everything at once
- Pause after each deliverable and wait for feedback
- This ensures alignment and catches issues early

---

## MVP Philosophy

### What MVP Means Here
✅ **DO THIS:**
- Fulfill all required points
- Code that works and is readable
- Basic error handling
- Clear comments where logic is non-obvious

❌ **DON'T DO THIS:**
- Pixel-perfect UI polish
- Exhaustive edge case handling (unless critical to core functionality)
- Over-engineering or premature optimization
- "Nice-to-have" features

### When to Stop
If a feature *does the job as described*, stop and move on. You can improve it later if time permits.

## Progress Tracking
